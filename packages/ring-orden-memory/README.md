# Ring Orden Memory

MIT implementation of confirmed transaction correction detection, extraction, reliability scoring, lexical/embedding retrieval and context assembly. Merchant mappings remain private; code is open source. No fine-tuning is performed.

Run from the monorepo root:

```sh
npm install
node --experimental-strip-types --test packages/ring-orden-memory/tests/*.test.ts
node --experimental-strip-types packages/ring-orden-memory/examples/correction.ts
```

`src/index.ts` exports `detectCorrection`, `extractCorrection`, `scoreMemory`, `retrieveMemories`, `buildMemoryContext`, `approveMemory`, `editMemory`, `disableMemory`, `mergeObservation`, `recordMemoryUse`, `reliabilityLevel`, and `cosineSimilarity`.

Every retrieval requires `merchant_id`. Pass `catalog` as well as optional `catalog_item_ids` to filter unavailable or removed products/modifiers. Correction meanings accept catalog product/modifier identifiers, quantities 1–50, allowed operation intent, and semantic item references; arbitrary instructions, prices, tenant IDs and payment changes are rejected. Retrieval excludes unconfirmed/inactive records and deleted products, then ranks phrase overlap or supplied embedding cosine with reliability, repeated observations, approval and recent confirmation. Embeddings are optional and must be generated by your own chosen model. The default implementation is lexical similarity, not a claim of neural semantic search.

Persist records using your database adapter. Confirmation is a trusted application event, not a claim from model output. Extract a candidate during a correction, then call `extractCorrection({...candidate, confirmed_by_customer:true})` only after the final transaction is confirmed. Never learn personal contact information. Approvals/edit/disable require merchant management authorization in the API; deletion removes the record from your database. Keep a separate audit event without personal data.

One confirmation creates NEW evidence. Repeated observations create OBSERVED. At least three observations and two successful uses, with failures no more than one third of successes, create TRUSTED. Merchant approval creates MERCHANT_APPROVED. Disabled entries are never retrieved. A successful retrieval means a confirmed transaction accepted the retrieved mapping, not merely that a query returned it.

See the complete example and tests for independent use with your own database/model. `../openmodel-gateway/evals/run.ts` compares the deterministic demo parser with and without retrieved correction evidence. These results are not live-model benchmark claims.
