# Customer automation and public capabilities

Implemented as private extensions of the existing canonical tenant state. The backend remains the only durable source of orders, customers, capability grants and notification jobs. n8n stores no customer database and never interprets or reconstructs an order.

## Persistence contract

`TenantState.customer_automation?: AutomationState` contains `jobs` and optional purpose-specific `grants`. Grant records contain token digests only. Outbox bearer URLs are AES-256-GCM encrypted using a purpose-derived SHA-256 key from `AGENT_TOOL_SECRET`; tenant, job and purpose are authenticated associated data. Never expose this state, phones, encrypted payloads or grants through merchant bootstrap or generic order metadata. Do not log claimed job messages or save n8n execution data.

Every recognized automation tool mutates state (including expiry processing during an empty claim). The route must load the authenticated tenant, call the helper, persist with repository optimistic concurrency, and only then return its result. A failed CAS must return a conflict without returning links or claimed jobs. Callers may retry a fresh load; never send an unpersisted claim. `handleAutomationTool` returns `undefined` for unknown tools without mutation. Public capability billing POST persists internally with CAS; its GETs are read-only.

Exported helpers:

- `queueCustomerAutomation(state, {order_id, purpose:'recovery'|'receipt'|'billing', consent:true}, env)` is asynchronous and returns a safe job summary. Only explicit true authorizes a notification; stored phone recognition is not identity verification. Recipient is read from the canonical same-tenant order, never supplied by the caller. Requires an E.164 customer phone and configured service secret of at least 16 characters. One durable job per order/purpose prevents duplicate voice requests from generating extra messages or replacing a queued grant.
- `claimAutomationJobs(state, {worker_id,limit?}, env)` is asynchronous. Maximum batch is ten. Returns only due valid jobs, a random claim token, stable job ID as provider idempotency key, recipient and message. Persist before dispatch. No fiscal values are included.
- `ackAutomationJob(state, {job_id,claim_token,outcome,provider_message_id?})` accepts `sent`, `retryable_failure`, `permanent_failure`, `unknown`. `sent` requires a provider message ID and means accepted, not delivered. An identical acknowledgement is idempotent; wrong claim tokens conflict.
- `handleAutomationTool(state,tool,body,env,session?)` supports `customer_followup`, `claim_automation_jobs`, `ack_automation_job`. Follow-up requires `{session_id,purpose,consent:true}` and uses the stored session's exact order. Passing a bound session prevents session switching. Authenticated routes must authorize worker tools separately from caller voice access.
- `queueCustomerVerification(state,session,consent,env)` requires explicit true and the exact saved session/order. It obtains a digest-only ten-minute challenge from the shared customer domain and queues its encrypted URL for delivery. The voice response contains only safe job status, never the token or URL. Duplicate requests reuse only a valid unconsumed challenge whose job is QUEUED/CLAIMED/RETRY/SENT. A fresh explicitly consented request may create a new generation after expiry, consumption, failure or an uncertain result; it invalidates earlier pending challenge links and preserves old UNKNOWN send evidence for reconciliation. No new generation is created by background retry. Consumed/replaced/expired challenges cannot dispatch. Parent voice routing should return already-verified state without enqueueing, and can invoke this helper when `verify_customer` includes `consent:true`; otherwise report that verification needs consent and delivery.

Rotating `AGENT_TOOL_SECRET` invalidates pending encrypted payloads. Such jobs become `FAILED/OUTBOX_DECRYPTION_FAILED`; no delivery is claimed and they are never silently resent. Rotate after draining jobs, or explicitly reconcile and arrange new capabilities. This version has no automated replay/reset of terminal jobs or provider reconciliation; operators must resolve ambiguity before any new contact.

## Recovery

`issueRecoveryLink(state,order,env)` resolves the canonical saved order by ID and only accepts unpaid DRAFT/AWAITING_CLARIFICATION/AWAITING_CONFIRMATION states. It changes the existing order-specific grant, never order contents or identity. The grant expires **exactly 600,000 milliseconds from issue**. `issueCustomerOrderLink` has an optional TTL argument and retains its existing one-hour default.

The queued recovery message points at the same saved draft. Draft completion, phone change, revoked/replaced grant, or expiry cancels dispatch. No snapshot, clone, repricing or automatic final confirmation occurs in automation; the existing customer order UI validates edits and confirmation. Recovery can be explicitly requested through the voice follow-up tool; telephone disconnect event ingestion/automatic detection requires separate provider integration and is not claimed live here.

## Receipt and billing grants

`issueCustomerCapabilityLink(state,order,'receipt'|'billing',env)` creates a random purpose-specific capability with one-hour lifetime and returns `/customer?purpose=...#token` on exact configured `CUSTOMER_APP_ORIGIN`. It never uses or creates an editable order grant, including for completed receipts. Reissuing the same purpose revokes previous grants. URLs carry bearer tokens only in the fragment; requests use the Authorization header. Digest records are private.

`handleCustomerCapability(request,env,repo)` recognizes only the routes below and otherwise returns `undefined`. Intercept these routes before merchant authentication and before the generic `/api/customer/*` order handler. Exact-origin CORS, no-store responses, no-referrer policy, strict token scope and expiry apply. OPTIONS does not require a token; data and mutation requests do. Missing Origin is allowed for non-browser clients holding the capability; browser Origin values must match exactly.

| Route                        | Operation                      | Allowed data                                                                                                                                                                                                                                                                         |
| ---------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/api/customer/receipt` GET  | Safe order summary             | Merchant name/currency, order reference, item names/quantities/prices, totals, status/payment status, expiry. No phone, identity history, grants, tax profile or editable operations.                                                                                                |
| `/api/customer/billing` GET  | Form status                    | Purpose, PENDING/ON_FILE, required field names, expiry. Never reads fiscal values.                                                                                                                                                                                                   |
| `/api/customer/billing` POST | Save confirmed billing profile | Required `rfc,legal_name,postal_code,tax_regime,cfdi_use,confirmed:true`; optional `email` (omitted/blank means absent). Strict size limit 16 KiB. Calls the shared customer-domain billing helper for the canonical order's customer. Returns only `{status:'ON_FILE',saved:true}`. |

A billing submission uses the capability once. Identical submissions return the same acknowledgement; a different replay requires a fresh grant. This confirms data submission, not contact verification or fiscal validation, and does not issue an invoice. Invoice provider work remains a separate authorized state machine. Backend `CUSTOMER_APP_ORIGIN` must match the deployed customer app; no request-provided return URL is accepted.

Billing GET lists the five fiscal keys in `required_fields` and `email` in `optional_fields`. A replay with omitted versus blank email is equivalent and does not create another billing profile or invoice request. Invoice requests still require the explicit authorized `request_invoice` action.

Receipt notification enqueue requires explicit receipt-specific consent. `queueCustomerAutomation` records `consent_at` in the private receipt job. There is no automatic verified-payment/completion trigger in this module; any server trigger must first resolve already-persisted receipt consent for the same customer/order and pass through the same deduplicating queue. Payment evidence alone never establishes notification consent, and general contact recognition or marketing flags must not be treated as receipt authorization.

## Retry and unknown outcomes

Claims last at most two minutes and never beyond link expiry. Explicit non-delivery uses 30/60-second exponential backoff and at most three send attempts. Expired links never dispatch. A lost worker/expired claim becomes UNKNOWN and is not reclaimed. A timeout or ambiguous provider response is UNKNOWN rather than RETRY. A late positive acknowledgement with the original claim token can record actual provider acceptance without creating another send. This is deliberately at-most-one automatic attempt after an uncertain result, not a guarantee that every request is delivered.

`n8n/i-customer-automation.json` is inactive on import. It claims, splits, sends through a configured Meta-compatible WhatsApp endpoint, classifies provider evidence, and acknowledges. Only explicit HTTP 429 is automatically retryable; definite client rejection is permanent; 5xx, timeout, malformed/unknown response and 2xx without message ID are UNKNOWN. Provider send has no automatic retry. Stable Idempotency-Key does not establish provider support; audit the actual provider before activation. Current WhatsApp conversation/template requirements must be verified before live use. This implementation neither sends real customer messages nor configures live credentials.

Public n8n worker URLs are `/api/automation/claim_automation_jobs` and `/api/automation/ack_automation_job`; the API ingress maps them to internal authenticated tool handlers. The public voice namespace rejects `/api/tools/claim_automation_jobs` and `/api/tools/ack_automation_job` with 404. Configure `RING_ORDEN_API_ORIGIN` to the API-only public origin and `WHATSAPP_SEND_URL` to the full audited provider HTTPS messages endpoint (for example, your account-specific Meta Cloud API endpoint, never a restaurant/customer URL). Credentials remain named Header Auth entries. The schedule stays inactive: one-minute polling is 60 executions/hour and must be checked against the actual n8n plan before activation.

The workflow also checks the link deadline immediately before the provider request and stops on an expired/invalid deadline. A stopped worker leaves the claim for backend UNKNOWN reconciliation rather than risking a late or duplicate send. Backend expiry/claim checks still apply on every poll.

## Verification

Tests exercise exact recovery TTL and unchanged one-hour grants; canonical order preservation; consent/phone/draft requirements; durable reload/idempotency; duplicate claims and acknowledgement matching; backoff/unknown outcomes/expiry; outbox encryption and key changes; purpose boundaries, origin/expiry/integrity; completed receipt privacy; billing submission idempotency and no fiscal read-back; and n8n evidence classification. Live WhatsApp delivery, n8n activation, public deployed origin and telephone disconnect processing are separate checks.
